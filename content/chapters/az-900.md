# 第二篇　AZ-900 必備知識

> ［考綱權重］雲端概念 25%\~30%；Azure 架構與服務 35%\~40%；Azure 管理與治理 30%\~35%。新版技能清單自 2026 年 7 月 20 日起適用。

## 第 1 章　雲端概念

### 1.1　一句話定位

AZ-900 的雲端概念不是考你背行銷詞，而是要你從責任、成本、彈性與維運負擔判斷適合的部署模型與服務模型。

### 1.2　部署模型

| 模型                       | 定義                                                                 | 適合情境                                   | 常見陷阱                                     |
| -------------------------- | -------------------------------------------------------------------- | ------------------------------------------ | -------------------------------------------- |
| 公用雲端（Public Cloud）   | 由雲端服務提供者擁有並營運基礎設施，多個客戶共享整體平台但邏輯隔離。 | 快速擴展、依使用量付費、減少自建機房。     | 「公用」不表示所有人都能讀取你的資料。       |
| 私人雲端（Private Cloud）  | 雲端基礎設施專供單一組織使用，可位於自有機房或代管環境。             | 高度控制、特定法規或既有整合需求。         | 仍需負擔較多硬體與維運責任。                 |
| 混合式雲端（Hybrid Cloud） | 結合公用雲端與私人／內部部署環境，並讓資料與工作負載協同運作。       | 分階段移轉、資料駐留、尖峰擴充、災難復原。 | 不是單純「兩邊都有系統」，重點是整合與協同。 |

### 1.3　共同責任模型

不論採用哪一種雲端服務，客戶始終要對資料、帳號、身分與存取管理負責。服務模型越往 SaaS 移動，Microsoft 承擔越多底層平台責任；但「上雲」從來不等於「責任消失」。

| 服務模型 | 資料與身分 | 應用程式／設定         | 作業系統  | 實體主機  | 資料中心  |
| -------- | ---------- | ---------------------- | --------- | --------- | --------- |
| 內部部署 | 客戶       | 客戶                   | 客戶      | 客戶      | 客戶      |
| IaaS     | 客戶       | 客戶                   | 客戶      | Microsoft | Microsoft |
| PaaS     | 客戶       | 共用／依服務而定       | Microsoft | Microsoft | Microsoft |
| SaaS     | 客戶       | 共用／設定責任仍在客戶 | Microsoft | Microsoft | Microsoft |

> ［必背］IaaS 題目出現「修補客體作業系統、安裝應用程式、防毒與網路規則」時，多半是客戶責任；PaaS 題目出現「平台修補與執行階段」時，多半由 Microsoft 負責；資料分類、帳號與存取權限仍是客戶責任。

### 1.4　成本與消費模型

| 概念              | 重點                                           | 考題提示                                     |
| ----------------- | ---------------------------------------------- | -------------------------------------------- |
| 資本支出（CapEx） | 先購買機房、伺服器與設備，成本前置且資產折舊。 | 自建機房、大額一次性投資。                   |
| 營運支出（OpEx）  | 依使用量支付日常服務費，可隨需求調整。         | 雲端用量、訂閱與持續性費用。                 |
| 消費式模型        | 用多少付多少；停止或縮小資源通常可降低費用。   | 不保證一定便宜，若資源長期閒置仍會產生成本。 |

### 1.5　雲端效益辨析

| 概念                          | 核心意義                                      | 關鍵字                                               |
| ----------------------------- | --------------------------------------------- | ---------------------------------------------------- |
| 高可用性（High Availability） | 讓服務在故障時仍盡量可用。                    | 多個執行個體、可用性區域、負載平衡。                 |
| 可擴縮性（Scalability）       | 增加或減少資源容量。                          | 垂直擴充是換大／換小；水平擴充是增加／減少執行個體。 |
| 彈性（Elasticity）            | 依需求快速或自動擴縮。                        | 尖峰自動擴充、離峰自動縮減。                         |
| 可靠性（Reliability）         | 系統在失敗後恢復並持續提供預期功能。          | 跨區域復原、備援、容錯設計。                         |
| 可預測性（Predictability）    | 效能與成本可透過工具、SLA 與監視規劃。        | 不是保證固定成本，而是可估算與控管。                 |
| 管理能力（Manageability）     | 透過入口網站、命令列、API、範本與自動化管理。 | 管理雲端與雲端管理兩層含義都可能出題。               |

### 1.6　IaaS、PaaS、SaaS 與 Serverless

| 類型       | 典型例子                                       | 控制／責任                                | 題幹特徵                                 |
| ---------- | ---------------------------------------------- | ----------------------------------------- | ---------------------------------------- |
| IaaS       | 虛擬機器、磁碟、虛擬網路                       | 最高控制、最高維運負擔                    | 需要自訂作業系統或既有應用程式搬遷       |
| PaaS       | App Service、Azure SQL Database、Azure Storage | 專注應用程式與資料；平台由 Microsoft 管理 | 快速開發，不想維護作業系統               |
| SaaS       | Microsoft 365、Dynamics 365                    | 直接使用完整應用程式                      | 只想使用功能，不管理平台與應用程式程式碼 |
| Serverless | Azure Functions 等                             | 依事件執行；平台自動配置與擴縮            | 間歇性、事件驅動、短時間工作             |

> ［易錯］Serverless 不代表沒有伺服器，而是使用者不需要管理伺服器。它通常仍屬於 PaaS 思維，但考題會把「事件觸發、依執行計費、快速自動擴縮」當成明顯線索。

## 第 2 章　Azure 架構與服務

### 2.1　實體架構與管理階層

| 名詞                            | 定義                                         | 考題焦點                           |
| ------------------------------- | -------------------------------------------- | ---------------------------------- |
| 資料中心（Datacenter）          | 包含實體伺服器、網路與電力設施的建築或園區。 | 最底層實體位置。                   |
| 區域（Region）                  | 由一個或多個鄰近資料中心組成的地理範圍。     | 建立多數資源時要選區域。           |
| 可用性區域（Availability Zone） | 區域內具獨立電力、冷卻與網路的實體位置。     | 防範單一資料中心／區域內位置故障。 |
| 區域配對（Region Pair）         | Microsoft 為部分區域建立的地理配對關係。     | 災難復原、平台更新排序等概念。     |
| 主權區域（Sovereign Region）    | 為特定政府或法規需求隔離營運的 Azure 區域。  | 資料主權與特殊合規要求。           |

| 由上而下                     | 用途                                       |
| ---------------------------- | ------------------------------------------ |
| 管理群組（Management Group） | 跨多個訂用帳戶套用治理、Policy 與 RBAC。   |
| 訂用帳戶（Subscription）     | 計費、配額與存取控制的重要界限。           |
| 資源群組（Resource Group）   | 資源的邏輯容器；資源只能屬於一個資源群組。 |
| 資源（Resource）             | VM、儲存體帳戶、VNet 等實際服務執行個體。  |

> ［口訣］管理群組管多個訂用帳戶；訂用帳戶管計費與配額；資源群組管生命週期與邏輯分類；資源才是實際服務。

### 2.2　計算服務

| 服務                        | 定位                                               | 題幹線索                                    |
| --------------------------- | -------------------------------------------------- | ------------------------------------------- |
| Azure Virtual Machines      | 完整作業系統控制；適合 lift-and-shift 或特殊軟體。 | 要自行管理客體 OS、修補與多數應用程式設定。 |
| VM Scale Sets               | 管理一組相同 VM，依負載自動擴縮。                  | 大量相同執行個體與水平擴充。                |
| Availability Sets           | 將 VM 分散於 fault domains 與 update domains。     | 傳統區域內可用性設計；不是跨區域。          |
| Azure Virtual Desktop       | Azure 上的桌面與應用程式虛擬化。                   | 遠端桌面、集中化桌面體驗。                  |
| Azure App Service／Web Apps | 受管理的 Web 應用程式與 API 平台。                 | 不想管理 OS，只部署 Web 程式。              |
| Containers                  | 封裝應用程式與相依性，共用主機核心，啟動快速。     | 可攜性、微服務、比 VM 輕量。                |
| Azure Functions             | 事件驅動的無伺服器運算。                           | 短時間、按事件、低維運負擔。                |

### 2.3　網路服務

| 服務                    | 功能                                 | 快速判斷                                   |
| ----------------------- | ------------------------------------ | ------------------------------------------ |
| Virtual Network（VNet） | Azure 中的邏輯隔離網路。             | 資源私有通訊與網路區隔。                   |
| Subnet                  | VNet 內的位址範圍切分。              | 依層級或用途分段。                         |
| VNet Peering            | 以 Microsoft 骨幹網路連接兩個 VNet。 | 低延遲私有連線；不自動傳遞路由。           |
| Azure DNS               | DNS 網域與名稱解析服務。             | 名稱解析，不是防火牆。                     |
| VPN Gateway             | 透過加密通道經公用網際網路連接。     | 成本較低、部署較快、品質受網際網路影響。   |
| ExpressRoute            | 透過連線供應商建立私有專線連線。     | 不走公用網際網路、可預測性較高、成本較高。 |
| Public Endpoint         | 服務透過公用 IP／公用網路端點存取。  | 可搭配存取控制，但仍是公用端點。           |
| Private Endpoint        | 將服務映射為 VNet 內的私人 IP。      | 私有連線到 PaaS 服務。                     |

### 2.4　儲存體服務、層級與備援

| 類型          | 適用情境                                                     |
| ------------- | ------------------------------------------------------------ |
| Blob Storage  | 物件儲存體；適合影像、影片、備份、記錄檔與大量非結構化資料。 |
| Azure Files   | 透過 SMB／NFS 提供受管理檔案共用。                           |
| Queue Storage | 大量訊息佇列，解耦應用程式元件。                             |
| Table Storage | NoSQL 索引鍵／屬性資料。                                     |
| Managed Disks | 供 Azure VM 使用的區塊儲存體。                               |

| 存取層級 | 判斷方式                                                        |
| -------- | --------------------------------------------------------------- |
| Hot      | 頻繁存取；儲存成本較高、存取成本較低。                          |
| Cool     | 較少存取；建議至少保存 30 天，提前刪除或轉層要收提前刪除費。    |
| Cold     | 比 Cool 更少存取；建議至少保存 90 天，同樣有提前刪除費。        |
| Archive  | 極少存取、離線層級；取回需要重新補水（rehydration）且延遲較高。 |

| 選項            | 複寫範圍                               | 考題重點                                    |
| --------------- | -------------------------------------- | ------------------------------------------- |
| LRS             | 單一主要區域內的單一資料中心           | 最低成本；不防資料中心整體災害。            |
| ZRS             | 主要區域內三個以上可用性區域           | 防可用性區域故障；不單獨防整個區域災害。    |
| GRS             | 主要區域 LRS＋非同步複寫到次要區域 LRS | 防區域災害；平時不可直接讀取次要區域。      |
| GZRS            | 主要區域 ZRS＋非同步複寫到次要區域 LRS | 兼顧主要區域跨區域與跨地理區域備援。        |
| RA-GRS／RA-GZRS | 在 GRS／GZRS 上加入次要區域唯讀能力    | 題幹要求「故障前就能讀取次要複本」時選 RA。 |

> ［口訣］L＝Local 單站；Z＝Zone 多區；G＝Geo 跨區域；RA＝Read Access，可讀次要區域。備援防硬體與位置故障，不等於防誤刪或勒索加密。

| 工具                   | 用途                                                            |
| ---------------------- | --------------------------------------------------------------- |
| AzCopy                 | 命令列大量複製 Blob／Files 資料。                               |
| Azure Storage Explorer | 跨平台圖形介面管理 Azure Storage。                              |
| Azure File Sync        | 把內部部署 Windows Server 檔案伺服器與 Azure Files 同步／快取。 |
| Azure Migrate          | 評估、探索與移轉伺服器、資料庫與 Web 應用程式。                 |
| Azure Data Box         | 用實體裝置傳輸大量資料，適合網路頻寬不足。                      |

### 2.5　Azure 身分、存取與安全

| 概念                            | 一句話定位                                                                       |
| ------------------------------- | -------------------------------------------------------------------------------- |
| Microsoft Entra ID              | 雲端式身分與存取管理；使用現代驗證、SSO、MFA、條件式存取。                       |
| Microsoft Entra Domain Services | 受管理網域服務，提供 LDAP、Kerberos、NTLM 與 Group Policy，支援舊式應用程式。    |
| SSO                             | 使用一次驗證存取多個受信任應用程式。                                             |
| MFA                             | 要求兩個以上不同類型的驗證要素。                                                 |
| Passwordless                    | 以 passkey、FIDO2、安全金鑰、Windows Hello 或 Authenticator 等方式避免傳統密碼。 |
| External ID                     | 讓合作夥伴、來賓或消費者安全存取應用程式與資源。                                 |
| Conditional Access              | 依使用者、裝置、位置、風險與應用程式等訊號，決定封鎖或要求額外控制。             |
| Azure RBAC                      | 控制誰能對哪些 Azure 資源執行哪些動作。                                          |

### 2.6　Zero Trust、縱深防禦與 Defender for Cloud

| Zero Trust 原則                 | 落地意義                                     |
| ------------------------------- | -------------------------------------------- |
| 明確驗證（Verify explicitly）   | 依可用訊號驗證與授權每次存取。               |
| 最低權限（Use least privilege） | 只給需要的權限、範圍與時間。                 |
| 假設入侵（Assume breach）       | 預設攻擊者可能已在內部，縮小影響並持續偵測。 |

縱深防禦的重點不是背出實體安全、身分與存取、周邊、網路、計算、應用程式、資料這七層清單，而是「單一控制被突破時，下一層還擋得住」這個判斷；題目常用「防火牆被繞過怎麼辦」這類情境測這個概念，不是要你逐層默寫。Microsoft Defender for Cloud 是把這套概念落地成可執行動作的工具：Secure Score 量化目前的安全態勢，安全建議指出哪裡沒做到位，再疊上法規符合性檢視與工作負載威脅防護。［易錯］看到「態勢管理、建議與評分」選 Defender for Cloud；看到「跨端點、跨身分的攻擊鏈關聯調查」才輪到 Defender XDR，題目常故意把兩者放在同一題考。

## 第 3 章　Azure 管理與治理

### 3.1　成本管理

| 成本因素         | 例子                                                                             |
| ---------------- | -------------------------------------------------------------------------------- |
| 資源類型與規格   | VM 大小、儲存體類型、資料庫服務層級。                                            |
| 使用量與執行時間 | 資源是否全天運作、交易與儲存容量。                                               |
| 區域             | 同規格資源在不同區域報價不同，部署前用 Pricing Calculator 核對，別假設全球同價。 |
| 網路流量         | 傳入 Azure 通常免費；傳出 Azure（egress）才是計費重點。                          |
| 授權與方案       | Windows／SQL 授權、預約、節省方案、混合權益。                                    |
| 支援方案         | 支援等級會影響總成本。                                                           |

Azure Pricing Calculator 用於部署前估算；Cost Management 用於部署後分析、分攤、預算與警示。Tags 可協助成本分類與報表，但不會直接建立安全界限，也不會自動阻止不合規資源。

### 3.2　Policy、RBAC、Locks 與 Tags

| 工具              | 主要問題             | 典型情境                                         |
| ----------------- | -------------------- | ------------------------------------------------ |
| Azure Policy      | 資源是否符合規則     | 限制區域、要求標記、稽核設定、拒絕不合規部署。   |
| Azure RBAC        | 誰能做什麼           | 授予 Reader、Contributor、Owner 等角色。         |
| Resource Lock     | 防止誤刪或誤改       | CanNotDelete 或 ReadOnly。鎖定可由有權限者移除。 |
| Tags              | 分類與中繼資料       | 成本中心、環境、擁有者；不是安全控制。           |
| Microsoft Purview | 資料治理、保護與合規 | 跨資料資產掌握、分類、保護與法規風險管理。       |

> ［最常考］Policy 管「資源是否符合規則」；RBAC 管「誰能做什麼」；Lock 管「即使有權限也先防誤刪／誤改」；Tag 管「如何分類與追蹤」。

### 3.3　管理與部署工具

| 工具                          | 定位                                                             |
| ----------------------------- | ---------------------------------------------------------------- |
| Azure portal                  | 瀏覽器圖形介面；適合互動式管理與探索。                           |
| Azure Cloud Shell             | 瀏覽器中的受管理命令列，提供 Azure CLI 與 Azure PowerShell。     |
| Azure CLI                     | 跨平台命令列；常見於 Bash 與自動化。                             |
| Azure PowerShell              | 以 PowerShell Cmdlet 管理 Azure。                                |
| Azure Arc                     | 把內部部署與其他雲端資源延伸納入 Azure 管理與治理。              |
| Infrastructure as Code（IaC） | 用宣告式檔案版本化並重複部署基礎設施。                           |
| Azure Resource Manager（ARM） | Azure 的部署與管理控制層；處理資源要求、權限、標記、鎖定與部署。 |
| ARM templates／Bicep          | 宣告式部署範本；Bicep 是較精簡的 Azure 原生 IaC 語言。           |

### 3.4　監視工具

| 工具                 | 主要功能                                               | 題幹關鍵字                       |
| -------------------- | ------------------------------------------------------ | -------------------------------- |
| Azure Advisor        | 根據成本、安全、可靠性、效能與營運卓越提出個人化建議。 | 「最佳化建議」                   |
| Azure Service Health | 顯示影響你資源的 Azure 服務事件、計畫維護與健康情況。  | 「Azure 平台事件」               |
| Azure Monitor        | 收集、分析與回應應用程式與基礎設施遙測。               | 「Metrics、Logs、Alerts」        |
| Log Analytics        | 在 Azure Monitor 中查詢與分析記錄資料。                | 「Log Analytics workspace、KQL」 |
| Azure Monitor Alerts | 依 Metrics、Logs 或 Activity Log 條件通知或觸發動作。  | 「條件成立就通知／自動化」       |
| Application Insights | 應用程式效能管理與分散式追蹤。                         | 「回應時間、例外、使用者體驗」   |

> ［口訣］Advisor 給改善建議；Service Health 告知 Azure 平台事件；Monitor 收集與分析遙測；Application Insights 專注應用程式。

## AZ-900 必背 20 句

- 客戶在所有雲端模型中都要對資料、帳號與存取管理負責。

- IaaS 給最多控制，也帶來最多客體作業系統與應用程式維運責任。

- PaaS 讓你專注程式碼與資料，不必管理底層作業系統。

- SaaS 是直接使用完整應用程式，但仍要管理使用者、資料與設定。

- Availability Zone 是區域內的獨立實體位置；Region 是地理範圍。

- 管理群組位於訂用帳戶之上，適合跨訂用帳戶套用治理。

- 一個資源只能屬於一個資源群組，但可移動到另一個資源群組。

- VM Scale Sets 適合大量相同 VM 的水平擴縮。

- Functions 的線索是事件驅動、無伺服器與按執行量。

- ExpressRoute 是私有連線；VPN Gateway 經由公用網際網路建立加密通道。

- Private Endpoint 讓 PaaS 服務以 VNet 中的私人 IP 存取。

- Blob 存物件；Files 提供檔案共用；Queue 傳訊息；Table 存 NoSQL 鍵值資料。

- ZRS 防區域內可用性區域故障；GRS／GZRS 才有跨地理區域複寫。

- RA 前綴表示可直接讀取次要區域。

- Entra ID 是雲端 IAM；Domain Services 是受管理的傳統網域能力。

- Conditional Access 是依訊號做「若……則……」的存取決策。

- Azure RBAC 是授權系統，核心是 security principal＋role definition＋scope。

- Policy 管合規規則；RBAC 管權限；Lock 防誤刪／誤改；Tag 管分類。

- ARM 是 Azure 管理控制層；範本與 Bicep 用於宣告式部署。

- Advisor、Service Health、Monitor 的題幹動詞分別是建議、平台健康、遙測。
